# Agents

## Build with Pi

Section owned by W8. Code: `backend/actron/flow/{build,context_pack,diff_check,test_runner}.py`, `backend/actron/workflows/build.py`, `backend/actron/activities/build.py`. Spec B, B9; contract B.C6.

**Protocol.** `BuildWorkflow` (task queue `build`) is the child of `RequestWorkflow`. It takes a B.C6 `BuildInput` dict and returns a `BuildResult` dict. It runs these steps in order:
1. Budget wait (`build_check_budget` → W6 `flow.budget.status`). When the daily cap is reached, it emits `build.step budget.wait`. It waits for the `budget_raised` signal or the next UTC midnight on a durable timer.
2. Queue. A Redis sorted set holds waiting builds and another holds running builds. One Lua script decides each move. Slots come from `ACTRON_MAX_CONCURRENT_BUILDS`. It emits `build.queued {buildId, position}` when the position changes. Position is the number of builds ahead.
3. `run_build` (`flow/build.py`). The same loop runs in-process (`LocalBuildSteps`) and in the workflow (`TemporalSteps`, one activity per step):
   - `prepare_checkout`: preflight checks for `missing_fork`, `missing_identity` and `no_model_key` before any clone or container. It clones the ingested repo to `<ACTRON_BUILD_HOST_DIR>/<buildId>/repo`. A missing target branch stops with `missing_branch`. It checks out the given `baseSha`, or else the target head. It creates `actron/<requestId>-r<n>`, or continues it when the branch is already on the push remote. It adds the push remote `actron-push`, lists files that differ from the working branch, and resolves the test command.
   - `write_build_context`: writes `ticket.json`, `evidence.json`, `procedures.json`, `code.md` (the context pack), `TASK.md` (the exact B9 text), `notes.md`, and `previous-build.md` when there is feedback. The previous build's notes, diff and tests are read from its folder when only `buildId` is given. It also writes `pack-meta.json` for the guards.
   - `run_pi`: see the command in `docs/runbook.md`, section Pi. Pi's JSON events stream into plain `build.step` events (`Reading …`, `Editing …`, `Running …`, `Asking the graph: callers(…)`), each with `file` and `detail`. The step heartbeats every 10 s. The timeout kills and removes the container, and so does activity cancellation.
   - `check_diff`, then `run_tests`, then a repair (failures.md) if needed, then `commit_and_push`, then `open_or_update_pr`.

**Enforcement** (`PiWatcher`):
- Exploration: `ls`, `find` and `grep` tools, shell `ls/find/grep/rg/cat/…`, and reads outside "Where to work", outside files Pi edited and outside `/context`. The 3rd exploration event records a reminder. The 10th stops the attempt (container killed), which is retried once with the reminder at the top of TASK.md. Counts go into `build.step` details and `result.guards`.
- Graph first: editing a file whose functions have callers needs a prior `callers`, `references` or `impact` call for them, or callers already in code.md (`callersInPack`). Otherwise a reminder is recorded and counted.
- Required outputs: a plan written to notes.md within the first 5 tool events, a valid `REPORT.json` (Pydantic schema `PiReport`), and the test command run after the last edit. A missing item fails the attempt. The repair's `failures.md` lists the missing items first, then failing tests, reminders and a summary of the previous attempt.
- Repairs: up to `maxRepairs`. Each repair reuses the same Pi session (`--session-id actron-<buildId>`, verified to resume) and also gets notes.md and failures.md.
- Model errors: Pi exits 0 on failed model calls. An attempt with only error turns ends the build with `model_error`.

**Guards**
- Weakened tests, in existing test files only. These count: a deleted file, a deleted test, fewer assertions, an always-true assertion, or a skip, xfail or only marker. This covers Python, JS/TS (`.test`, `.spec`, `-test.ts`, `__tests__`, `test/`) and Clojure (`deftest`, `is`, `^:skip`). The result is `stopped` with `tests_weakened`. Changing an expected value is allowed.
- Scope: changed files outside the affected functions' files, test-plan files, covering tests, test files and the procedure's co-changed paths go to J9 `is_scope_change`. A probability of 0.7 or more stops with `scope_change`. Without a model, the stub answers 1.0. A non-empty `STOP.md`, or `REPORT.stopped`, also stops with `scope_change`.
- Time: `timeoutSeconds` gives `failed` with `timeout`. An optional `maxTokens` gives `stopped` with `token_budget`.

**Isolation**
- The Pi container gets exactly one model key, the MCP URL and a run token (W5 `register_run_token`, Redis with a TTL). It never gets `GITHUB_TOKEN`, `SLACK_*`, `LINEAR_*`, `DATABASE_URL` or `ACTRON_SECRET_KEY`. Values are passed by name and never appear in argv. Tests check the command, the environment of the docker CLI, and the environment seen inside the container.
- Tests run in `actron-test-runner`. The prepare container has network and no credentials, and installs dependencies into `<host>/_deps-cache/<kind>-<lockfile hash>`. The run container uses `--network none`. Each container is created, inspected (network mode and env names are recorded in `TestResult.isolation`) and removed.
- The test command comes from the ticket, then the procedure, then the repository default. The source is recorded. Parsers: JUnit XML (pytest), Mocha JSON, Jest and Vitest JSON, and an exit-code fallback that keeps the last 200 lines.
- Push: the commit is made as `ACTRON_BOT_NAME <ACTRON_BOT_EMAIL>` with `-c` flags. `git push` uses a credential helper script that reads `GITHUB_TOKEN` from the environment of that git process only. The token is never in argv, the remote URL or `.git/config`.
- PR: GitHub REST against `GITHUB_API_URL`, only on the push target. It finds an open PR for the branch, otherwise POSTs `/repos/{fork}/pulls`. The body follows the B9 template plus a "Build report" with the REPORT.json contents.

## Investigator

Section owned by W5. Code: `backend/actron/flow/investigate.py` (entry point and fallback pipeline), `backend/actron/flow/investigator_agent.py` (the agent loop), `backend/actron/mcp_graph/{tools,server}.py` (the 20 graph tools), `backend/actron/graph/queries.py` (the named queries, see `docs/queries.md`). Spec B, B4 and B5; contracts B.C2, B.C3, B.C4.

**Entry point.** `investigate(ws, request_id, text, kind, *, emit, mode="auto")` returns `InvestigationResult(findings, label, summary, mode, tool_calls, tokens, cost_usd, stub, evidence, questions, investigation_id, fallback_reason)`. `mode="auto"` picks the agent when an agent model with a key is configured (`MODEL_AGENT`, checked through `actron.models.llm.available("agent")`), otherwise the pipeline. The freshness gate runs before this, in the request workflow (W6).

**Tools.** `search`, `get_node`, `callers`, `callees`, `impact`, `criticality`, `shortest_path`, `decisions_for`, `related_work`, `tests_for`, `owners`, `procedures_for`, `get_code`, `get_code_range`, `file_outline`, `find_symbol`, `references`, `history`, `get_code_at`, `search_code`. Each is a plain async function behind `call_tool(ctx, name, args)` with a Pydantic input model (the MCP schema is generated from it). Every call is read-only, limited to 2 seconds and 200 rows, drops secret-looking properties, cuts text above 4,000 characters, and emits `tool.called {callId, tool, args, by}` and `tool.result {callId, ok, summary, nodeIds, durationMs, error?}`. Errors come back as `{"error": {"code", "message"}}`. Code tools name the snapshot commit (`snapshot`) and mark files that differ on the build's target branch (`differs: true`). `history` reads `TOUCHED` links (following `RENAMED_TO` backwards) and falls back to `git log -L` on the clone; `get_code_at` runs `git show <sha>:<path>` and finds the symbol with W2's parser (a definition-line heuristic if the parser is missing).

**MCP server (verified on `mcp` 2.3.0, 17 Oct 2026).** The SDK renamed `FastMCP` to `mcp.server.mcpserver.MCPServer`. Tools are registered with `add_tool(fn, name, description, structured_output=False)`; each returns JSON text. The investigator connects in-process with `mcp.Client(server)` (`graph_client(tool_ctx)`). Pi connects over Streamable HTTP at `http://worker:8765/mcp` (`http_app()`, served by `serve_http()`, stateless JSON responses). Every HTTP request needs `X-Actron-Run: <token>`; `register_run_token(ws, ttl, request_id=…, snapshot_sha=…, differing_paths=…)` stores `mcp:run:<token>` in Redis, unknown tokens get 401, and each call reads only the token's workspace graph. Host-header checks accept `worker` and localhost only. Port 8765 is not published to the host in `infra/compose.yaml` (checked by a test).

**Agent loop.** System prompt: `backend/actron/models/prompts/investigator.md` (W4). The model gets the MCP tools as function schemas and calls them through the in-process client, at most 12 tool calls or 3 minutes; calls beyond the budget are answered with a budget error and the model is then asked, without tools, for its final JSON `{seedIds, decisionIds, relatedWorkIds, notes}`. Ids that no tool returned in this run are dropped. Seeds are rescored with J5 when more than 5 are proposed. Then `shared_query(seedIds)` builds the canonical findings, followed by the same J6, label, J8 and question steps as the pipeline. If the agent fails (model error, no JSON) it is retried once; after the second failure the pipeline runs and a second `investigation.started {mode: "pipeline", reason}` records why.

**Fallback pipeline.** `search` (full text, top 20 non-test candidates) -> J5 `rank_candidates` (seeds = "directly involved" or better; when J5 is a stub: `0.6 * full-text score + 0.4 * name match`, at least 0.45, at most 5) -> `shared_query` (each named query shown as a tool call) -> J6 `judge_conflict` per decision -> label (`flow/labels.py`) -> J8 `needs_question` -> questions. With no model at all, an approved decision that J6 could not judge counts as a possible conflict (0.5), never as a conflict; proposed and superseded ones count as none.

**Questions.** Only for feature and bug requests labelled `conflict` or `possible_conflict`, when J8 says input is needed (or the label is `conflict`). At most 3, each tied to evidence ids present in the findings; questions with no valid evidence are dropped. With an LLM: W4's `write_questions`. Without: one choice question per conflicting decision, "The team decided: “…” Should that still hold after this change?" (Yes, keep it / No, this request changes it). A critical seed with no decision gets a question about keeping behaviour for its callers. The target-branch question is added later by W6.

**Events, in order.** `investigation.started {mode}` -> `tool.called`/`tool.result` per graph query -> `judgment.made {job, provider, count, what}` for J5, J6 (one batched event) and J8 -> `evidence.found` per piece of evidence (conflicts, constraints, seeds, tests, similar work, owners, callers; one per node, max 40 events) -> `investigation.completed {label, summary, counts, findingsRef}`.

**Graph writes.** `Investigation` (summary, `conflictLabel` with `none` for nothing found and clear, tool call count, start and finish), `Request -[:HAS_INVESTIGATION]->`, `Request -[:ABOUT]->` each seed, and `Investigation -[:FOUND {role, rank, path}]->` each evidence node of an `Evidence` type (people are not `Evidence` nodes in the ontology, so owners stay in the findings only). If the request is not yet mirrored into the graph, a minimal `Request` node is merged.

**Tests.** `tests/unit/flow/test_investigator_agent.py` (scripted fake model), `test_pipeline.py`, `test_label_rule.py`, `tests/eval/test_investigation_sample.py` (fixtures `tests/fixtures/eval/requests.yaml` and `qa.yaml`; results written to `.actron/eval/investigation_sample.json`), `tests/integration/mcp/*`.
